01 · 고도화한 주제

무엇을 받아서 무엇을 내놓는가

처음 재료(토큰화 → 웹 검색 → URL → 크롤링, 빈도 강조, 메모리와 시계열)를 하나의 학습 루프로 묶었습니다. 비전공자도 AI 답변의 핵심 개념을 놓치지 않게 하는 것이 목표입니다.

입력

  • Claude Code 대화: 내 질문과 AI 최종 답변, 세션 ID, 작업 폴더, 시각 (설정 시트 참고)
  • 직무·전공 (선택, 노트의 예시와 비유에 사용)
  • 사용자 반응: 노트 열기, "개념이에요/아니에요" 확인, 복습 결과

출력

  • 중요도 표시: 답변 속 개념에 형광펜 3단계 (상·중·하)
  • 주간 개념 차트: TOP 10, 순위 변동, 상승·식는 중 신호, 새 개념 후보
  • 공부 노트: 한 줄 정의, 근거 문장과 출처 URL, 헷갈리는 개념, 내가 쓴 대화

핵심 루프

대화→개념 추출·정규화→중요도 산정→주간 차트→웹 근거 노트→확인·복습 피드백→다음 주 차트와 사전

빈도를 그대로 쓰지 않고 꾸준함(세션 단위), 희소성(IDF), 개념성(사전)으로 보정합니다. 사전에 없는 새 용어는 사용자가 한 번 확인하면 사전에 들어가고, 이 확인 기록이 나중에 학습형 랭커의 라벨이 됩니다.

이 구성을 고른 이유

  • 공식 훅 필드만 사용: 질문은 prompt, 답변은 Stop 훅의 last_assistant_message(2.1.47부터). 트랜스크립트 파일의 내부 형식에 기대지 않습니다.
  • 파일 인박스: 서버가 꺼져 있어도 기록이 빠지지 않고, 파이프라인은 원할 때 읽습니다.
  • Claude 작업에 영향 없음: 비동기 실행, 출력 없음, 실패해도 항상 정상 종료.
  • Windows 대응: 설치에 쓴 Python의 절대경로를 슬래시와 따옴표로 등록합니다. 훅이 Git Bash로 실행되면 역슬래시가 지워지고, python3 이름만 쓰면 스토어 별칭이 잡힐 수 있기 때문입니다.
  • 안전한 설치: 기존 settings.json 자동 백업, 다른 설정 보존, 다시 설치해도 중복 없음, --uninstall로 이 훅만 제거, --test로 자가 점검.

    • 색만으로 뜻을 전하지 않습니다. 등급 글자, 화살표, 텍스트 라벨을 함께 씁니다.
    06 · 개념 클릭 응답

    개념을 눌렀을 때 가볍게 보여 주기

    관련 개념과 기록을 한꺼번에 LLM에 넣으면 클릭할 때마다 토큰이 크게 늘어납니다. 클릭 응답은 로컬 색인에서 바로 만들고, 웹 검색은 매주 차트 상위 개념에만 미리 해 둡니다.

    웹 조회 방식 비교와 결정

    방식무게결정
    WebSocket (WSS)연결 유지, 재연결·상태 관리 필요쓰지 않음. 클릭은 요청 한 번이면 끝남
    SSE 스트리밍단방향, 일반 HTTP 그대로노트를 새로 만들 때 진행 표시용으로만
    HTTP + 캐시가장 가벼움기본
    사이트 전체 크롤링페이지 수십 개, 차단·파싱 위험쓰지 않음
    위키백과 요약 API키 없음, 무료, 정의 위주 문장1순위
    메타 검색 스니펫 (SearXNG)셀프호스팅, 요청 한 번위키백과로 부족할 때
    본문 추출 (trafilatura)페이지 1개근거 문장이 2개 미만일 때만

    응답 단계와 예산

    단계내용비용
    클릭 즉시정의 1줄과 출처, 관련 개념 3개, 내 기록 3개LLM 0토큰, JSON 약 0.8KB 실측
    더 보기기록·관련 개념 다음 3개 (커서)LLM 0토큰
    노트 새로 만들기캐시가 없을 때만: 근거 3문장·600자 이내 → 검증 에이전트LLM 입력 약 1천 토큰 이하 추정
    주간 배치차트 TOP 10만 미리 노트 생성개념 10개 × 위 비용

    관련 기록 20개와 웹 페이지 3개를 통째로 넣는 단순한 방식은 클릭 한 번에 1만 토큰을 쉽게 넘깁니다 추정. 이 구조에서는 클릭할 때 LLM을 부르지 않습니다.

    동작 확인 (네트워크 대신 모의 응답 사용): 위키백과 단계에서 HTTP 요청 2번으로 근거 문장 2개를 확보했고, 같은 개념을 다시 요청하면 캐시에서 HTTP 0번으로 돌려줍니다. 클릭 카드 JSON은 781바이트였고, 기록 14개를 3개씩 5쪽으로 중복 없이 넘겼습니다.
    07 · 검증 에이전트

    할루시네이션을 코드로 걸러내는 검증 에이전트

    노트를 문장 단위로 나눠 각 문장이 출처 문장으로 뒷받침되는지 확인합니다. 기본 검사는 모두 코드로 동작해 비용이 들지 않고, LLM이나 NLI 판정은 애매한 문장에만 선택해서 씁니다.

    노트추출형 또는 LLM 작성
    →
    문장 나누기Kiwi 문장 분리
    →
    근거 찾기내용어 포함률이 가장 높은 출처 문장
    →
    규칙 검사숫자, 영문 용어, 부정 표현
    →
    재생성 (최대 2회)걸린 문장과 이유를 피드백
    →
    마무리근거 있는 문장만, 부족하면 출처 문장 그대로

    판정 규칙

    판정조건처리
    근거 있음내용어 포함률 0.6 이상, 숫자·영문 용어가 출처에 있음, 부정 표현 일치출처 번호를 붙여 사용
    근거 없음출처에 없는 숫자나 영문 용어, 또는 포함률 0.35 미만재생성 피드백, 안 되면 삭제
    애매함그 사이, 또는 부정 표현이 출처와 반대판정기가 있으면 맡기고, 없으면 삭제

    충실도(근거 있는 문장 비율)가 1.0이면 그대로, 0.5 이상이면 근거 있는 문장만 남기고, 그 아래면 출처 문장을 그대로 노트로 씁니다. 판정기는 judge(claim, evidence) 함수 하나로 끼웁니다.

    동작 확인 실행

    출처: 트랜스포머 정의문 1개, 어텐션 정의문 1개. 일부러 틀린 문장 2개를 섞은 노트.

    노트 문장판정이유
    트랜스포머는 어텐션 메커니즘만으로 문장 속 단어들의 관계를 계산하는 신경망 구조다.근거 있음포함률 1.0
    2017년 논문에서 처음 제안되었다.근거 있음숫자 2017이 출처에 있음
    2019년 Google이 처음 공개했다.근거 없음출처에 없는 숫자 2019, 용어 Google
    트랜스포머는 순환 구조를 핵심으로 사용한다.애매함 → 삭제출처는 '순환 구조 없이'

    결과: 충실도 0.5 → 근거 있는 두 문장만 출처 번호와 함께 남김. 재생성 예시에서는 '2012년 AlexNet 논문에서 처음 정의' 문장이 걸렸고, 피드백 한 번 뒤 충실도 1.0이 됐습니다.

    한계: 단어 겹침 기반이라 같은 뜻을 완전히 다른 말로 쓴 문장은 '애매함'으로 빠질 수 있습니다. 그런 문장이 많으면 그때만 판정기(로컬 소형 NLI나 같은 LLM)를 켜면 됩니다. 이 검사는 근거 문장과의 일치만 보므로, 근거 문장 자체가 틀린 경우는 출처 신뢰도로 따로 다뤄야 합니다.

    • LLM: Ollama나 llama.cpp의 GGUF 4비트(Q4_K_M). 4B급(예: Qwen3 4B, Gemma 3 4B)이면 6GB GPU에 다 올라갑니다. 노트북에서는 CPU로 주간 배치만 돌립니다.
    • 임베딩·NLI: ONNX Runtime 동적 int8 양자화(quantize_dynamic)로 크기를 약 1/4로 줄이고 CPU에서 추론합니다.
    • 랭커·로지스틱 회귀: 이미 KB 단위라 양자화가 필요 없습니다.
    • 메모리 상한: 기본 구성은 Kiwi가 대부분인 약 0.5GB. LLM을 켜도 약 4GB 안쪽입니다.

    비용 0원 설정

    • 검색: 위키백과 요약 API (키 없음, 같은 사이트는 1초에 1번) → 필요하면 셀프호스팅 SearXNG. 유료 검색 API 없이 시작합니다.
    • LLM: 기본은 추출형이라 LLM이 없어도 됩니다. 쓰면 로컬 Ollama. 무료 티어 API로 바꿔도 구조는 같고, 한도는 바뀔 수 있어 쓰기 전에 확인합니다.
    • 저장: 인박스 JSONL 1개 + SQLite 파일 2개 (색인, 웹 캐시).
    • 서버: 로컬 FastAPI나 Streamlit 하나.
    • 밖으로 나가는 데이터: 개념 이름(검색어)뿐입니다.
    가장 크게 아끼는 곳은 양자화가 아니라 클릭할 때마다 LLM을 부르지 않는 구조입니다. 양자화는 LLM을 켰을 때 내 컴퓨터에서 돌리기 위한 장치입니다.

    10 · 시뮬레이터 A 실측

    중요도 산정 방식 선정

    관심 궤적(핵심, 상승, 하락, 일회성 몰림, 가끔)을 심은 가상 사용자의 12주 대화를 생성하고, 각 방식이 앞으로 2주 동안의 실제 관심을 얼마나 잘 맞히는지 비교했습니다. 평가용 3명 × 시드 5개 × 8개 시점 = 개 시점, 가중치 선택은 별도의 무작위 사용자 명으로 했습니다.

    정답을 '미래 관심'으로 둔 이유: 일회성으로 몰려 물어본 개념은 빈도가 높아도 다음 주에는 다시 안 나옵니다. 차트는 '다음 주에도 붙잡아야 할 개념'을 보여 줘야 하므로 미래 관심을 정답으로 삼았습니다.

    모델 리더보드: 가중치를 바꿔 직접 고르기

    기준별 점수를 방법들 사이에서 0~1로 정규화해 가중합합니다. "라벨 없이 바로 가능"은 학습형 랭커처럼 실사용 라벨이 필요한 방법에 감점합니다.

    종합 점수 순위

    모든 방법은 같은 전처리(사전 매칭 + Kiwi + 정규화)를 거친 토큰에 개념성 가중치(사전 밖 단어 0.35, 제안 수식은 튜닝값)를 곱해 산정 함수만 비교했습니다. 전처리 없이 세는 순수 빈도는 아래 요소 제거 실험의 마지막 줄들처럼 더 낮습니다. NDCG@10: 미래 관심을 이득으로 쓴 순위 품질. 잡음: TOP 10 중 개념이 아닌 단어 비율. 버스트 오탐: 일회성 몰림 개념이 몰림 이후 TOP 10에 남은 비율. 상승 포착: 곧 뜰 개념을 미리 TOP 10에 올린 비율. 하락 잔존: 이미 식은 개념이 남은 비율. 주간 변동: 지난주 대비 TOP 10 교체율 (실제 관심의 교체율은 ).

    학습형 랭커(HistGradientBoosting, 특징 15개, 학습 행, CPU 1초 미만)는 제안 C보다 NDCG가 높습니다 (95% CI ). 다만 같은 생성기로 만든 가상 사용자에게서 배운 결과라 생성기의 가정까지 학습했을 수 있습니다.

    11 · 시뮬레이터 B 실측

    동의어 병합: '오버피팅'과 '과적합'은 같은 개념인가

    같은 개념의 표기 쌍 개, 표기가 비슷하지만 다른 개념인 혼동쌍 개(정밀도/정확도, GPT/GPU, 트랜스포머/트랜스퍼 러닝 등), 무작위 쌍 개로 평가했습니다. 학습형은 개념 단위 5겹 교차검증이라 처음 보는 개념에서 측정됩니다.

    방법별 ROC-AUC
    0.5는 무작위 추측
    학습 없음특징 결합 학습

    결론

    문자열 유사도는 혼동쌍을 같은 개념으로 묶어 버립니다. 정적 단어 벡터(spaCy 한국어 floret)도 AUC 로 거의 무작위입니다. 12개 특징을 묶은 로지스틱 회귀가 AUC 로 가장 낫지만, 혼동쌍의 를 여전히 잘못 병합합니다.

    그래서 병합의 1순위는 별칭 사전이고, 모델은 새 표기를 '같은 개념 후보'로 제안만 합니다. 신경 임베딩(다국어 문장 임베딩)과 혼동쌍 대조학습은 GPU 환경에서 같은 데이터로 비교해야 합니다 미실측.

    학습 없는 방법은 교차검증으로 고른 임계값이 대부분 '전부 같은 개념'으로 쏠려 F1·재현율이 부풀려집니다. 이 방법들은 ROC-AUC로 비교하세요.

    위 7쌍은 표기가 비슷하지만 다른 개념, 아래 7쌍은 표기가 전혀 다르지만 같은 개념입니다.

    12 · 시뮬레이터 C 실측

    공부 노트의 근거: 크롤링한 문장 중 정의문 고르기

    개념 개마다 정의문 1개와 같은 용어가 들어간 비정의문 3개(경험담, 방법·조언, 평가·여론)를 섞은 문장 코퍼스에서, "OO이란 무엇인가?" 질의로 정의문을 1위에 올리는지 봤습니다. Q2는 다른 표기(주로 영어)로 질의한 경우, '+확장'은 별칭 사전으로 질의를 넓힌 경우입니다.

    결론

    검색 점수(BM25, 문자 n-gram, 단어 벡터)는 '용어가 들어간 문장'을 찾을 뿐 정의문을 고르지 못합니다 (Q1 Hit@1 BM25 ). '…이란', '…의 약자', '…하는 방법이다' 같은 정의 패턴을 더하면 , 별칭 사전으로 질의를 확장하면 까지 오릅니다.

    영어 표기로 물으면 확장 없이는 모든 방법이 이하로 떨어집니다. 시뮬레이터 B의 별칭 사전이 여기서도 핵심입니다. 이 단계는 규칙만으로 충분해 파인튜닝이 필요 없습니다.

    편향 주의. 이 코퍼스는 직접 작성해서 정답 정의문이 평균 자로 비정의문(자)보다 깁니다. 로지스틱 회귀의 가장 큰 계수가 '문장 길이'였고, 길이 특징을 빼면 Hit@1이 로 내려갑니다. 실제 크롤링 문장 100개 이상에 라벨을 붙여 다시 확인해야 합니다.

    4. 4일차 위키백과 요약 API + 캐시 → 정의 패턴으로 근거 문장 선택 (fetch_sources)
    5. 5일차 추출형 노트 + 검증 에이전트 (LLM은 선택, 로컬 4비트)
    6. 6일차 화면: 대화 하이라이트, 개념 차트, 노트 (Streamlit 또는 Next.js)
    7. 7일차 이 시뮬레이터로 회귀 테스트, 데모 시나리오 녹화

    스택

    • Python: kiwipiepy, scikit-learn, rank_bm25, trafilatura
    • 저장: SQLite (대화, 개념 로그, 노트, 확인 기록)
    • API: FastAPI 또는 Streamlit 단일 앱

    • 검색: 위키백과 요약 API(키 없음) + SQLite 캐시, 필요하면 SearXNG

    • 가상 로그: 관심 궤적과 템플릿 발화로 만든 데이터라 결과가 생성기 가정에 기대고 있습니다. 실제 대화 2~4주를 모아 같은 지표로 다시 재야 합니다.
    • 사전 커버리지 85% 가정: 사전에 빠진 개념()은 차트에서 밀립니다. 데모의 간호사 사용자는 상승 중인 '임베딩'이 사전 밖이라 차트 대신 후보 큐에 나옵니다.
    • 미실측 모델: 이 환경에서는 Hugging Face 모델 다운로드가 막혀 다국어 임베딩, 재랭커, LLM을 측정하지 못했습니다. 같은 벤치마크를 GPU 환경에서 돌려 리더보드에 추가하는 것이 다음 단계입니다.
