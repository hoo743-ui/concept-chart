# 학습 실험 가이드라인 (실제 데이터로 모델을 학습해 성능을 계속 확인할 때)

Claude Code로 실험할 때 이 문서와 `CLAUDE.md`를 먼저 읽고 따른다.
목표는 하나다: **지금 방식보다 실제 데이터에서 나아졌는지를, 같은 기준으로, 반복해서 확인한다.**

## 1. 무엇이 나아질 수 있나 (시작 전 기대치)

시뮬레이터는 모델이 아니라 시험장이다. 정답이 우리가 만든 가상 데이터라서, 시뮬레이터 점수가 오르는 것과 실제로 좋아지는 것은 다르다. 개선은 **실제 데이터의 시험 세트**에서만 판단한다.

| 부품 | 지금 방식 (시뮬레이터 점수) | 학습으로 바꿀 후보 | 기대 |
|---|---|---|---|
| B 용어 정규화 (같은 개념인가) | 로지스틱 회귀 12개 특징: AUC 0.824, 어려운 오답 오판 17.9%, 한↔영 재현율 69.3% | 사전학습 다국어 인코더 미세조정 (쌍 대조 학습) | 높음 — 한↔영 재현율이 지금의 약점 |
| C 근거 문장 (정의문 고르기) | 로지스틱 회귀 13개 특징: MRR 0.975, Hit@1 0.967 (개념 30개, 가상 문장) | 사전학습 한국어 인코더 분류기·재순위 | 중간 — 시뮬레이터는 이미 천장이라 실제 웹 문장에서만 확인 가능 |
| A 중요도 순위 | 제안 C 공식: NDCG@10 0.845, 일반어 침입 4.8% (GBM 0.910이지만 안정성 때문에 보류) | 학습형 랭커 | 낮음 — 정답(사용자 반응) 데이터가 쌓이기 전에는 근거가 없다 |

## 2. 기준선 먼저

1. 실제 데이터를 받으면 **지금 방식부터** 그 시험 세트에서 돌려 점수를 낸다. 이것이 진짜 기준선이다.
2. 새 모델은 같은 시험 세트, 같은 지표로만 비교한다. 지표는 시뮬레이터와 같게: B는 AUC·AP·어려운 오답 오판율·한↔영 재현율, C는 MRR·Hit@1·Hit@3.
3. 차이는 부트스트랩 95% 신뢰구간과 함께 보고한다 (시뮬레이터 A의 `boot_diff`와 같은 방식).

## 3. 데이터 분할

- 학습 / 검증 / 시험을 **개념 단위로** 나눈다. 같은 개념이 두 세트에 걸치면 점수가 부풀려진다 (시뮬레이터의 GroupKFold와 같은 이유).
- 분할은 시드를 고정해 한 번 만들고 파일로 저장한다. 이후 바꾸지 않는다.
- 시험 세트는 마지막 판정에만 쓴다. 하이퍼파라미터·조기 종료는 검증 세트로만 고른다.
- 데이터 출처·라이선스·받은 날짜를 실험 기록에 적는다.

## 4. 학습 원칙

- 처음부터 학습하지 말고 **사전학습 모델을 미세조정**한다 (데이터가 적을 때 과적합을 줄인다).
- 학습 손실을 끝까지 내리는 것이 목표가 아니다. **검증 지표가 더 안 좋아지면 멈춘다** (조기 종료). 학습 손실만 계속 내려가면 과적합 신호다.
- 손실 함수는 문제에 맞춘다: B는 쌍 분류(이진 교차 엔트로피) 또는 대조 학습, C는 문장 분류(이진 교차 엔트로피) 또는 순위 손실.
- 시드 고정 (`random`, `numpy`, `torch`), 패키지 버전 기록.

## 5. Mac (Apple Silicon)에서 학습

```python
import torch
device = "mps" if torch.backends.mps.is_available() else ("cuda" if torch.cuda.is_available() else "cpu")
```

- 지원 안 되는 연산이 있으면 실행 전에 `export PYTORCH_ENABLE_MPS_FALLBACK=1` (그 연산만 CPU로).
- MPS는 float64를 지원하지 않는다. float32로 둔다.
- 설치: `python -m pip install torch` (SETUP.md 8단계). 실험이 자리 잡으면 실제 쓴 버전을 `requirements-ml.txt`로 고정해 커밋한다.

## 6. 실험 기록 (성능을 계속 확인하는 방법)

실험을 시작할 때 아래 구조를 만든다 (지금은 없음 — 첫 실험에서 만든다).

```
experiments/
├─ splits/                     고정한 학습·검증·시험 분할 (개념 목록)
├─ <날짜>-<이름>/
│  ├─ config.json              데이터 출처, 모델, 하이퍼파라미터, 시드, git 커밋, 패키지 버전
│  └─ metrics.json             검증·시험 지표 + 기준선 대비 차이와 신뢰구간 + 추론 속도·메모리
└─ RESULTS.md                  실험마다 한 줄 (날짜 · 이름 · 핵심 지표 · 기준선 대비 · 채택 여부)
```

- 모델 가중치·체크포인트는 git에 올리지 않는다 (`.gitignore`: `models/`, `*.pt`, `*.pth`, `*.safetensors`, `*.onnx`, `*.gguf`). 기록(config·metrics·RESULTS.md)만 커밋한다.
- 실험 결과는 `sim/results/`나 `page_data.json`에 섞지 않는다. 결과 페이지 숫자는 사용자 결정 없이 바꾸지 않는다.

## 7. 파이프라인에 붙이는 규칙 (구조를 깨지 않게)

- 새 모델은 **기존 방식을 지우지 않고 비교 행으로 추가**한다 (시뮬레이터 B·C의 방법 목록, 또는 같은 지표 함수를 쓰는 실험 스크립트).
- 실제 사용 경로(`kit/`)에 넣을 때는 같은 모양의 함수로 감싼다: B는 `same_concept(a, b) -> 확률`, C는 `definition_score(term, sentence) -> 점수`. `kit/`는 다른 폴더를 import하지 않는다는 규칙(`docs/ARCHITECTURE.md`)을 지킨다.
- 무료·경량 원칙: 추론은 CPU 또는 Mac GPU에서 돈다. 크면 int8 양자화(ONNX)를 검토한다.
- 바꿀 때마다 `python dev.py check` 통과 → 브랜치 → CI → main, `CHANGELOG.md`에 한 줄.

## 8. 채택 기준 (사용자가 최종 결정)

모두 만족할 때만 기본 경로를 바꾼다.

1. 실제 시험 세트에서 지금 방식보다 좋고, 차이의 95% 신뢰구간이 0을 넘는다.
2. 어려운 경우(B: 발음이 비슷한 다른 개념)가 나빠지지 않는다.
3. 추론 속도·메모리가 예산 안이다 (예산 값은 사용자가 정한다).
4. 결과를 `experiments/RESULTS.md`에 남기고 사용자가 승인한다.

## 9. Claude Code에 맡길 때

- 긴 학습을 돌리기 전에 계획(데이터·분할·모델·지표·예상 시간)을 먼저 보여 주고 승인을 받는다.
- 시험 세트와 분할 파일은 수정하지 않는다.
- 점수는 기준선 행과 신뢰구간을 같이 보고한다. 확인하지 않은 숫자는 쓰지 않는다.
