# Decision Log — 개념 차트

양식: AI:GO OT 슬라이드의 다섯 항목(왜 AI를 썼는지 · 무엇을 물었는지 · 무엇이 나왔는지 · 무엇을 왜 골랐는지 · 무엇으로 확인했는지).
숫자는 `experiments/` 결과 파일에서 가져왔다. 시험 세트는 쓰지 않았고, 모두 검증·평가 세트 값이다.

## D1. 표기 합치기 모델을 서비스에 켜지 않는다 (2026-11-09)

- **왜 AI를 썼나:** `인덱스`와 `index`처럼 표기가 다른 같은 개념을 규칙만으로 합치기 어렵다고 봤다.
- **무엇을 물었나:** 두 표기가 같은 개념인가 (MiniLM 파인튜닝, 글자 CNN·BiLSTM, 로지스틱 회귀).
- **무엇이 나왔나:** 공개 개발 용어집(1,634쌍) AP는 파인튜닝 0.805, BiLSTM 0.777, CNN 0.767, 로지스틱 회귀 0.720. 위키백과 검증 세트의 0.934는 낙관적이었다. 내 대화 시트(사용자가 정답을 단 147쌍, 같은 쌍 4개)에서 파인튜닝은 1쌍을 맞히고 약 43쌍을 잘못 합쳤다.
- **무엇을 왜 골랐나:** 켜지 않는다. 잘못 합치면 다른 개념의 순위와 노트가 섞인다. 처음 생각한 모델은 공개 용어에서는 작동했지만 실제 대화에서 풀던 문제가 드물었다.
- **무엇으로 확인했나:** `experiments/2026-11-09-b-finetune/eval_all.json`. 두 번째 시트는 모델이 고른 쌍이라 편향이 있고, 세션이 2개뿐이다.
- **버린 것:** 어휘를 그대로 넓힌 데이터(BiLSTM 어려운 오답 오판 0.349 → 0.717), 별칭을 정리한 데이터(파인튜닝 AP 0.774, r2보다 낮음).

## D2. 오탐의 핵심은 개념 추출이었다. 개념 관문을 넣는다

- **왜 AI를 썼나:** `커밋`과 `추천`을 가르는 규칙을 다 만들 수 없다.
- **무엇을 물었나:** 이 낱말이 이 문장들에서 전문 용어로 쓰였는가 (`qwen3:4b`).
- **무엇이 나왔나:** 낱말 413개, 정답 116개 기준 없음 0.28, 사전만 0.75, 규칙 0.93, LLM만 0.72, 첫 채택안 0.96. 그런데 뒤에 쌓인 처음 보는 낱말 약 56개를 Claude가 읽어 보니 약 0.70이었다 (`서비스, 조건, clean`). 규칙이 조정 데이터에 과적합됐다. 소문자 영어를 LLM 확인으로 돌리고 LLM 질문을 엄격하게 바꾼 뒤, 먼저 고정한 정답으로 다시 쟀다: 조정용 412개 정밀도 0.98·재현율 0.37, **처음 보는 428개 정밀도 0.92·재현율 0.53**. LLM 없이 규칙과 사전만 쓰면 처음 보는 낱말에서 0.66이다.
- **무엇을 왜 골랐나:** 규칙이 확신하거나 사전과 LLM이 함께 인정한 낱말만 공부 목록에 넣는다. 사용자가 오탐을 가장 싫어하므로 재현율을 일부러 낮췄다. LLM이나 사전 혼자 인정한 낱말은 숨김 목록의 후보로 보내 사용자가 올릴 수 있게 했다.
- **이전 결정 변경:** 11-08 결정 "개념 = 명사 + 코드 용어, 사전 없음"을 바꿨다. 개념 사전(정답 목록)은 여전히 없지만, 공개 데이터의 기술 용어 목록을 근거 중 하나로 쓴다. 사용자가 방향을 맡긴 뒤의 변경이고 되돌릴 수 있다.
- **무엇으로 확인했나:** 정답을 결과 전에 고정했다(`data/eval/concept_gold.txt`). 다만 **정답은 Claude가 표시했고 사용자 검토 전이며**, 규칙의 일반어 목록은 같은 낱말을 보며 만들어 낙관적이다.

## D3. 비용 없는 로컬 LLM: Ollama + qwen3:4b

- **왜 AI를 썼나:** 출처 문장을 초보자가 읽기 쉽게 바꾸고 답변을 요약해야 한다.
- **무엇을 물었나:** 6GB GPU에 들어가고, 무료이며, 서비스에 쓸 수 있는 모델.
- **무엇이 나왔나:** EXAONE 3.5는 레지스트리 기준 비상업 라이선스, Gemma 3는 자체 약관, Qwen3는 Apache 2.0.
- **무엇을 왜 골랐나:** `qwen3:4b`. 라이선스가 명확하고 크기가 2.5GB다. 한국어 품질 비교는 하지 않았다.
- **무엇으로 확인했나:** 413개 판정이 199초에 실패 0건으로 끝났고, 그동안 GPU 메모리 약 4GB, RAM 여유 5GB 이상이었다.

## D3-1. LLM이 글을 쓸 자리를 줄였다

- **무엇이 나왔나:** 낱말 겹침 대조와 전체 테스트를 통과한 노트를 직접 읽었더니 `GPU 메모리 사용량이 2.36GB로 0.04GB의 온도를 보입니다`, `LoRA는 기존 모델에 추가 파라미터 없이…`, `마이크로소과프트`가 있었다. 문장을 원문에서 거의 그대로 가져온 요약은 정확했다.
- **무엇을 왜 골랐나:** 요약은 번호 선택만 맡긴다(새 문장 없음). 쉬운 설명은 근거 한 문장으로 제한하고 명사 전부 대조 + 두 번째 확인을 건다. LLM이 쓰던 대화 맥락 설명·기억할 점·퀴즈는 뺐다. 확인 문제는 출처 문장의 빈칸으로 바꿨다.
- **버린 것:** "내 대화와 같은 뜻인가"를 예/아니요로 묻는 판정. 18건이 전부 아니요로 나왔다. 분야 판정과 3지선다 대상 판정으로 바꿨다. "모르면 빈 문자열" 지시도 빈 응답만 늘려 뺐다.
- **무엇으로 확인했나:** 재생성한 노트를 다시 읽었다. 실제 오류를 회귀 시험으로 남겼다(`tests/test_study.py`). 이 확인은 Claude가 읽은 22건 범위이고 전수 평가가 아니다.

## D4. LLM 파인튜닝은 지금 하지 않는다

- **왜 고민했나:** 사용자가 파인튜닝 또는 전체 요약 파이프라인을 원했다.
- **무엇을 왜 골랐나:** 전체 요약 파이프라인. 좋은 요약의 정답 데이터가 없어 파인튜닝해도 좋아졌는지 잴 수 없다. 표기 합치기에서 공개 데이터 점수가 실제 대화와 달랐던 경험도 있다.
- **대신 준비한 것:** 사용자 판단(`judgments`), 이해 표시(`progress`), 통과·탈락 기록(`study_notes`)이 쌓인다. 이것이 나중의 학습 데이터가 된다.
- **다시 볼 조건:** 통과 문장이 너무 적거나, 사용자 판단이 수백 건 이상 쌓였을 때.

## D5. 프론트·백엔드·모델을 나눈다

- **무엇을 왜 골랐나:** 사용자 요구. 화면은 `app/`에서 `api.js`로만 통신하고, 서버는 화면을 모르며, 모델은 별도 프로세스에서 `jobs` 표로만 일을 받는다.
- **무엇으로 확인했나:** `tests/test_study.py`가 의존 방향을 검사한다. LLM 없는 모델 이름으로 서버를 켜도 모든 API가 응답함을 시험한다.

## D8. 개념 관문을 분야 무관으로: 분야 사전 + 위키백과를 두 번째 근거로 (사용자 결정 "넣어서 진행해", 2026-11-10)

- **왜 고민했나:** 사용자가 "사용자가 어떤 질문을 해도" 서비스가 되어야 한다고 했다. 이전 관문은 개발 용어 사전에 기대서 경제·의학·법 답변에서 재현율이 0.09였다.
- **어떻게 쟀나:** `experiments/2026-11-10-general-gate/`. qwen3:4b가 만든 답변 49개(조정용 경제·의학·법·역사·생물, 처음 보는 화학·심리학·회계·음악·지구과학), 정답은 Claude가 관문 결과를 보기 전에 표시(사용자 검토 전). 라운드마다 같은 정답으로 재고, 처음 보는 분야는 마지막에 한 번만 열었다.
- **라운드 (조정용 정밀도·재현율 / 개발 대화):** r0 0.70·0.09 / 0.916·0.415 → r1 분야 무관 질문 + 위키백과 0.495·0.675 / 0.828·0.448 → r2 우리말샘 0.719·0.597 / 0.856·0.454 → r3 기초 어휘 0.730·0.597 / 0.856·0.454. 처음 보는 분야: 0.667·0.500, AI 없음 0.646·0.553.
- **버린 것:** 섞임 낱말을 전문 뜻 비중으로 가르기 — 조정용 세트에서 비중이 높은 낱말(결합·활성화·저항)이 오히려 정답이 아니었다.
- **알고 남긴 약점:** 처음 보는 분야 오탐의 상당수는 대문자 약어 규칙이 화학식 조각(CH·OH·SO)을 통과시킨 것. 이 세트는 이미 열었으므로 고친 뒤에는 새 분야로 다시 재야 한다. 일상 뜻도 있는 전문어(산화·이온·자산)는 후보로만 간다. 개발 대화 정밀도는 0.06 내려갔다.
- **r4 화학식 조각 (11-10):** 첨자가 바로 뒤에 붙은 영문 낱말을 숨겼다. 조정용 0.742·0.597. 새 분야 세트(물리학·천문학·철학·언어학·환경과학, 규칙을 고친 뒤 처음 열었다): 0.672·0.562, AI 없음 0.621·0.450. 이미 본 처음 세트는 참고로 0.717·0.500.
  새 세트에서 남은 오탐: 아래첨자 x(NOₓ → NO)와 숫자가 붙은 조각(PM2.5 → PM), 사람·별 이름(데카르트·허블·시리우스), 학문 이름(천문학·언어학), '-적' 꼴(열역학적), 사전에 전문어로 실린 일상어(미세먼지·이산화탄소). 놓친 것 35개 중 26개가 섞임 낱말(입자·중력·전류)이고 그중 18개는 위키백과 문서도 있었다.
  개발 대화 점수(0.703)는 그사이 대화가 늘어 정답이 없는 새 낱말 114개가 '아님'으로 채점된 값이라 비교하지 않는다 (예전 낱말만 대략 다시 세면 오탐 14 → 10). LLM 질문 예시와 겹친 3낱말(번역·통과·형태소)은 새 세트 채점에서 뺐다.
- **r5 (11-10):** 개발 대화 점검을 정답 만든 시각(11-09 20:28) 이전 낱말 840개로 고정했다 (기준선 0.902·0.454). 조정용 세트로만 고른 채택안: '-적' 꼴 숨김 + 아래첨자 글자 → 조정용 0.754·0.597, 개발 대화 그대로, 새 분야(본 세트) 0.692·0.562.
  버린 안 (조정용·개발 대화로 확인): 두 글자 대문자를 LLM 확인으로 돌리기(오탐 CC·VS는 빠지지만 AI·DB·PC를 잃음), 바로 뒤 숫자를 조각으로 보기(SGLT2의 SGLT를 잃음), 섞임 낱말에 LLM + 위키백과 문서면 보여 주기(금리·혈액·재판도 문서가 있어 조정용 정밀도 0.754 → 0.531. 새 분야 세트만 보면 좋아 보였던 안이다).
- **r6 '더 보기' 살리기 (11-10, 사용자 결정 "2번으로 진행해"):** 조정용에서 놓친 것 중 14개가 '전문 뜻만 + LLM 아님'(민법·세균·산업혁명). LLM 질문이 엄격해서다. 두 번째 질문(`everyday_prompt`: 보통 성인이 아는 일상어인가)을 전문 뜻만 + LLM 아님 + 위키백과 문서인 낱말에만 던져 '일상어 아님'이면 살리는 안(V3): 조정용 0.746·0.688, 개발 대화 0.866·0.459, 새 분야(본 세트) 0.653·0.613.
  재현율이 오르는 대신 정밀도가 1~4점 내려가서, 기본 목록에는 넣지 않고 질문 묶음의 접힌 칸에만 둔다 (`gate.rescue`, `gate.extra`). 그래서 공부 목록 수치는 r5 그대로다. 늘어난 오탐(상속·징역·혈압·가이드라인·변압기)은 정답 경계가 애매한 낱말이 많아 사용자 정답 검토 뒤 다시 잰다.
  버린 안: 전문 뜻만 + 위키백과 문서면 LLM을 무시(V1, 조정용 정밀도 0.659), 두 번째 질문을 LLM 인정 낱말에도 던져 일상어면 숨김(V2, 재현율 0.468로 떨어짐). 실험 코드 `experiments/2026-11-10-general-gate/everyday.py`.
  다음 (사용자 결정 "가"): 분야 사전의 분야를 LLM 질문에 힌트로 주는 안(V4)을 같은 세 세트에서 V3와 비교한다.
- **V4 분야 힌트 (11-10, 버림):** V3와 같은 낱말에 judge_prompt + "국어사전에 ○○ 분야 전문 용어로만 실려 있다" 한 줄로 다시 물었다. 조정용 0.729·0.662 (V3 0.746·0.688), 개발 대화 0.867·0.464 (V3 0.866·0.459), 새 분야(본 세트) 0.691·0.588 (V3 0.653·0.613).
  고르는 기준인 조정용에서 V3가 두 수치 모두 앞서 V3를 그대로 둔다.
- **정답 기준 (11-10, 사용자가 유형별로 정함):** 의학·법률 용어는 흔한 말(혈압·징역·상속)도 개념. IT는 서버·세션·배포·부팅·클라우드·라벨·토글·엔진·캔버스·랭크까지 개념, 폴더·로그인·브라우저·업데이트·백업·버전·데스크톱·잠금·문맥·확장은 아님. 학문 이름은 개념, 사람·별·나라 이름은 아님, 역사 사건은 개념.

## D7. 배포: 설치 파일 하나 + 첫 실행 흐름 (사용자 결정, 2026-11-10)

- **사용자 결정:** "웬만하면 사용자에게 설치파일을 하나로 묶어서 한번 설치하면 끝나는 식으로". 첫 실행 흐름(컴퓨터 점검 → 받기 → 입구 고르기 → 과거 대화 가져오기 동의)으로 간다.
- **묶을 것과 라이선스 (2026-11-10 확인):** Python 패키지 `kiwipiepy`·`kiwipiepy_model`·`trafilatura` Apache-2.0(설치된 패키지 메타데이터), Ollama MIT(GitHub 저장소), `qwen3:4b` Apache-2.0(`ollama show --license`), 우리말샘 파생 사전 CC BY-SA 2.0 KR(출처 표시, 파생 사전은 같은 라이선스). 모두 재배포 가능하고, 설치 파일에 라이선스 고지 파일을 넣어야 한다.
- **크기 (이 PC 실측):** Ollama 설치 폴더 3.3GB(파일 989개, GPU 라이브러리 포함), `qwen3:4b` 약 2.5GB, 사전 35MB. 전부 한 파일에 넣으면 6GB가 넘는다.
- **사용자 결정 (같은 날 이어서):** 전부 넣으면 너무 크다 → 작은 앱(AI 없이 약 150~200MB, 추정) + AI는 첫 실행에서 원하는 사람만 받기. 화면은 **앱 창 방식**: 안에서는 지금의 로컬 서버(`localhost`만)가 돌고, OS에 들어 있는 웹 화면 기능(Windows WebView2 등)으로 자기 창을 띄운다. Electron은 쓰지 않는다(100MB 이상 늘어남). 웹사이트 방식은 대화 원문이 서버로 가고 GPU 비용이 들어 택하지 않았다.
- **사용자 결정: 앱 본체 + Claude Code 플러그인 입구.** 본체는 위의 앱 창 설치 파일(파이썬 포함, Claude Code를 닫아도 동작, 다른 AI 답변도 받음). 플러그인은 가벼운 입구로 Stop 훅의 `last_assistant_message`를 앱에 넘기고 앱 창을 여는 명령만 둔다(파이썬·사전 없음). 플러그인만으로 가지 않은 이유(공식 문서 확인, 2026-11-10): 파이썬이 따라가지 않고, 백그라운드 실행(monitor)은 세션이 끝나면 멈추며, Claude Code 사용자만 쓸 수 있다.
- **디자인·UI/UX는 사용자가 나중에 직접 꾸민다.** 그때 바로 손댈 수 있게 화면(`app/`)은 서버와 API 계약(`docs/API.md`)으로만 연결된 상태를 유지한다.
- **아직 정할 것:** 지원 OS 순서. AI 없이 측정한 정밀도(다음 측정)를 보고 AI 받기를 얼마나 권할지.
